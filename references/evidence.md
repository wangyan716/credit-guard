# 方法说明：这些数字是怎么来的

复现：`python scripts/audit.py --deep`。全过程只读，不改任何原始文件。

## 两套账本，别混用

| 账本 | 位置 | 用来回答 | 覆盖 |
|---|---|---|---|
| 账单口径 | `~/.workbuddy/workbuddy.db` → `session_usage.credit_json` | 总量、哪一类、哪个会话 | 全量 |
| 结构口径 | `~/.workbuddy/projects/*/*.jsonl` → `providerData.rawUsage` | 为什么贵（输入/输出/模型/轮次） | 45%~100% |

- `credit_json` 是「每请求 id → 积分」的映射，请求 id 全局唯一（已校验：960 个 id 无一跨会话重复）。
- jsonl 会截断/轮换，部分请求没写 `rawUsage`，所以结构口径只是**样本**。
- 两套账本方向一致，排序一致；**绝对量不能相加**。

`audit.py` 里：
- 默认模式只读 DB，约 1 秒，输出分类 + 排名 + 每日趋势；
- `--deep` 追加扫 jsonl，约 7~10 秒，输出基座成本、模型单价、上下文随轮次膨胀。

## 关键指标的算法

| 指标 | 算法 |
|---|---|
| 会话基座 | 每个会话第 1 次请求的 `prompt_tokens` 均值 |
| 上下文膨胀 | 按请求在会话内的序号分档（1 / 2-5 / 6-15 / 16-40 / 41-100 / 100+），各档输入 token 均值 |
| 模型单价 | Σcredit ÷ Σprompt_tokens × 1,000,000 |
| 空转率 | `automation_runs.thread_title` 命中「无新 / 无待处理 / 静默结束 / total=0」的比例 |
| 长会话 | 单会话请求数 > 100 |

## 一个真实账号 5 个月的分布（已匿名化）

| 类别 | 占全部积分 |
|---|---:|
| 无人值守自动化 | 58% |
| 超长会话（2 个） | 36% |
| 有人参与·常规 | 6% |

机制：
- 输入占单次请求成本的 99%（输出中位数 185 token，输入中位数约 51k）。
- 第 1 轮约 47k token；41-100 轮时均值 222k（4.7 倍），单次积分 2.9 → 10.7。
- >120k 输入的请求占 30%，吃掉 52% 的积分；最大单次 428k 输入 = 109 积分（≈ 40 次普通会话）。
- 模型单价：Pro 78 / Auto 94 / 中档 53 / Flash 14 / 快速 11（积分每百万输入 token）。
- 缓存命中：0/1,776 次请求读到缓存。

## 未验证 / 估算项（别当结论用）

- 基座里技能索引约 12k token、工具 schema 最大一组约 22k token，是**按字节数估算**，未逐项验证注入量。
- 「缓存 0 命中」是 provider 未上报还是确实没命中，未验证；按全量重算对待是保守假设。
- 收益测算的百分比按实测单价外推，非 A/B 实测。
