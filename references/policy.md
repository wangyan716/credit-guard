# 积分节流策略（细则）

SKILL.md 的 R1~R7 是规则，这里是细则：判定树、阈值、模板、收益测算。

## 一、判定树：这笔消耗该不该花

```
这次请求，输入会有多大？
├─ < 60k  → 正常，照做
├─ 60k-120k → 先问：能不能少读点？能不能换会话？（一次请求约 2-3 积分）
└─ > 120k → 停。必须先把上下文压下去：
      ① 结论写进文件，开新会话；
      ② 大文件改用脚本过滤，只读摘要；
      ③ 只保留「接下来要动的那几个文件」。
      单次 428k 输入 = 109 积分，够 40 次普通会话。
```

```
这个活非 Pro 不可吗？
├─ 是格式搬运 / 跑命令 / 改一处代码 / 查一个字段 → 快速
├─ 是要做取舍、找根因、写正式文档 → Pro / thinking
└─ 不确定 → 快速先跑；卡住一次再升级
```

```
这个自动化值得每天跑吗？
├─ 有明确「有新东西才干活」的判据 → 可以，但必须用脚本判，不用模型判
├─ 只是「万一有呢」 → 不要建。改成用户触发（说一句就查）
└─ 已经存在的高频轮询 → 降频到 1 次/天，或加前置探测
```

## 二、阈值表（本机实测校准，2026-11-10）

| 指标 | 正常 | 警戒 | 处置 |
|---|---|---|---|
| 单次请求输入 | < 60k tok | > 120k tok | 换会话 / 压缩上下文 |
| 单会话轮次 | < 40 | > 100 | 写交接单，换新会话 |
| 单会话累计积分 | < 50 | > 300 | 拆任务 |
| 单会话基座 | 47k tok ≈ 2.9 积分 | — | 关掉不用的插件/连接器 |
| 单日总积分 | < 30 | > 150 | 查是不是自动化在空转 |
| 自动化空转率 | < 30% | > 60% | 加前置探测或直接停 |
| 模型单价（积分/百万输入） | 快速 11 · Flash 14 · Hy4 53 | Pro 78 · Auto 94 | 例行活换快速 |

## 三、自动化设计模板（照抄）

目标是「没有活的时候，花 0 积分」。关键是**把判断搬到模型之外**。

```bash
# 第 0 步：一条命令判断有没有活（不进模型语义层）
hit=$(curl -s -m 5 -H "Authorization: Bearer $TOKEN" http://host/api/pending | python -c "import sys,json;print(json.load(sys.stdin).get('total',0))")
if [ "$hit" = "0" ]; then
  echo "NOOP"; exit 0        # 自动化 prompt 的第一句话：读到 NOOP 就 send_automation_result 并结束
fi
```

prompt 里第一段固定写：

```
先执行 scripts/probe.sh。输出 NOOP → 调用 send_automation_result("无变化，跳过")，不要读任何文件、不要解释。
输出非 NOOP → 才进入下面的处理步骤，且只处理本次新增的部分。
```

另外三条：
- `rrule` 必须显式带时间：`FREQ=DAILY;BYHOUR=9;BYMINUTE=0`。**不要用 `FREQ=HOURLY;INTERVAL=24`**（实测被按小时跑，一天 23 次）。
- 一个自动化只挂一个 cwd；多目录用多实例，别扇出。
- 每轮结果写一行到 `runs.log`（时间 + 有无产出 + 耗时），月度看一眼空转率。

## 四、交接单模板（换会话时用）

```markdown
# 交接 2026-11-10 14:30

## 目标
<一句话：这次要做完什么>

## 已完成
- <3-5 条，带文件/接口名>
- 例：指标卡组件已改（src/components/KpiCard.tsx）

## 未完成
1. <带原因的未完成项，按优先级>
2. 例：分项数值口径不一致，差异在 wind 字段

## 关键路径
- 代码：<仓库绝对路径>
- 服务：<地址 + 账号位置（别写明文密码）>
- 产物：<部署包/文档位置>

## 下一步
<第一条要执行的具体动作，最好是一条命令>
```

新会话开场：`读 <交接文件路径>，从「下一步」开始` —— 一句话即可，不要粘贴历史。

## 五、收益测算（按实测比例外推）

| 动作 | 依据 | 预计效果 |
|---|---|---|
| 停掉/降频空转轮询 | 自动化占总量 58%，其中 90% 零产出 | **-50%~-55%（历史区间）**；当前月只剩每天一两次时可忽略 |
| 长会话 40 轮换新 | 超长会话占 36%，单次积分 10.7 → 2.9 | **-25%~-30%** |
| 例行活换快速模型 | Pro 78 vs 快速 11 积分/百万输入 | 该部分 **-70%~-85%** |
| 上下文不超 120k | >120k 请求占 30% 却吃 52% 积分 | **-30%~-40%** |
| 合并碎片会话 | 1009 个会话各付约 2.9 基座 | 每合并 10 个会话省约 26 积分 |
| 关掉不用的插件/连接器 | 基座约 47k，技能索引 ~12k + 工具 schema 最大组 ~22k | 每请求 **-20%~-40%**（**估算**） |

**月度目标**：把「两个反模式」从 94% 压到 20% 以内，总量降 **80% 以上**。
降不下去，几乎一定是又长出了一个 R1 或 R2 型消耗 —— 跑 `audit.py --days 30` 就能看见。

## 六、自查节奏

- 每周一：`audit.py --deep --out ~/WorkBuddy/credit-report-$(date +%Y%m).md`

- 每次要开新会话做大任务之前：看一眼基座和模型选择
